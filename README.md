# Сверка договоров поставки

Прототип для тестового задания Product Owner, Semantic TextNavigator. Закупщик загружает TXT-файлы с договорами, допсоглашениями и письмами и получает таблицу: номер договора, поставщик, сумма и срок поставки на дату проверки. У каждого значения есть имя файла, точная цитата и ссылка на абзац исходного текста.

**Демо:** https://maxborland.github.io/supply-terms-checker/. Нажмите «Загрузить пример» или перетащите свои TXT-файлы.

## Запуск

Зависимостей нет. Нужен любой статический сервер, потому что ES-модули не загружаются по `file://`.

```bash
git clone https://github.com/Maxborland/supply-terms-checker.git
cd supply-terms-checker
python -m http.server 8000   # или: npx serve .
```

Откройте http://localhost:8000.

Тесты (Node.js 20+, без пакетов):

```bash
npm test
```

## Как пользоваться

1. Загрузите TXT-файлы кнопкой или перетаскиванием. Кнопка «Загрузить пример» подставляет 6 учебных документов из `documents/`. Файл с тем же именем заменяет ранее загруженный.
2. Дата проверки по умолчанию 10.03.2026, её можно поменять. Таблица пересчитывается сразу.
3. В таблице у каждого значения есть ссылка «файл, п. N». Клик раскрывает исходный документ внизу страницы и подсвечивает абзац.
4. Колонка «Не согласовано / требует проверки» показывает проекты, предложения из писем, ДС с будущей датой вступления в силу и конфликты.
5. Блок «Вопросы»: четыре кнопки с вопросами из задания и две формы для любых договоров («поле по договору» и «поставка раньше даты»).

Ответы на вопросы задания на примере:

| Вопрос | Ответ прототипа | Основание |
|---|---|---|
| Срок STN-101 на 10.03.2026 | 30.04.2026, изменён ДС № 1 (было 15.04.2026). Проект ДС № 2 с 10.05.2026 не подписан | `02_amendment_signed.txt`, п. 2; `06_amendment_draft.txt`, п. 2 |
| Сумма STN-102 | 840 000 ₽. Аванс 252 000 ₽ помечен как «не является суммой договора» | `03_contract.txt`, п. 2.1 и 2.2 |
| Сумма STN-103 | нет данных. Лимит бюджета 600 000 ₽ помечен как «не является суммой договора» | `04_contract.txt`, п. 2.1 и 2.2 |
| Поставка раньше 01.04.2026 | только STN-102 (20.03.2026); есть несогласованное предложение поставщика перенести на 27.03.2026 | `03_contract.txt`, п. 3.1; `05_supplier_email.txt` |

## Как это устроено

```
TXT-файлы ──▶ parseDoc: абзацы, тип, статус, даты подписания и вступления в силу
               │
               ▼
          связь с договором по номеру из заголовка (иначе из текста)
               │
               ▼
          resolve: значения из договора
               + подписанные ДС, вступившие в силу к дате проверки (по дате вступления)
               → остальное в «не согласовано» (проекты, письма, ДС из будущего)
               → конфликты и неподписанный договор в «требует проверки»
               │
               ▼
          таблица + ответы на вопросы + исходный текст с якорями
```

- `parser.js` — вся логика, чистые функции. Работает в браузере и в `node --test`.
- `app.js` — интерфейс: загрузка, таблица, вопросы, переход к абзацам.
- `index.html` — разметка и стили.
- `test/parser.test.js` — 11 проверок: четыре вопроса, «нет данных», статус документа, дата вступления в силу, новый договор, переименованные файлы, неоднозначные значения.
- `documents/` — 6 учебных документов из задания.

Ответы, суммы, даты и имена файлов в код не вшиты. Тип документа определяется по заголовку и строке «Статус», связь с договором по номеру в тексте. Имена файлов и порядок загрузки на результат не влияют, это проверяет тест.

Поле описывается одной записью в `FIELDS` (`parser.js`): какие абзацы о нём, какие абзацы похожи, но не про него (аванс, лимит, оплата), и как достать значение. Новое поле, например ставка неустойки, добавляется так же.

## Известные ограничения

- Правила рассчитаны на формат учебных документов: заголовок первой строкой, строка «Статус: …», формулировки «общая стоимость», «обязуется поставить не позднее», «вступает в силу». Документ другого вида попадёт в «не распознан» или даст «нет данных», но не выдуманное значение.
- Сумма ищется только в рублях, дата только в формате ДД.ММ.ГГГГ.
- Подписанность определяется по фразе «подписан… обеими сторонами» в строке статуса. Подписи, печати и полномочия подписантов не проверяются.
- Если в одном абзаце несколько разных значений и нет конструкции «с X на Y» или «не позднее X», прототип не выбирает, а показывает «нужна проверка».
- Абзац, где сроку поставки сопутствует слово «оплата», пропускается (так отсекается срок оплаты). Если в реальных договорах эти условия пишут в одном предложении, правило придётся уточнить.
- Документы хранятся только в памяти вкладки, после перезагрузки их нужно загрузить снова. На сервер ничего не отправляется.
- Кодировка: UTF-8, при ошибке декодирования используется Windows-1251.

## Записка

### Для кого

Специалист по закупкам, который сверяет условия поставок по пакету документов: договор, допсоглашения, переписка. Его задача — быстро узнать действующие сумму и срок на дату и не пропустить изменения, которые ещё не оформлены. Цена ошибки — неверная претензия поставщику или пропущенная поставка, поэтому каждое значение подкреплено цитатой, а сомнительное помечено, а не угадано.

### Пять вопросов клиенту

1. В каком виде документы приходят на самом деле: TXT, скан, DOCX, выгрузка из ЭДО? Есть ли в ЭДО статус подписания, которому можно доверять больше, чем тексту?
2. Какие поля нужны кроме суммы и срока: неустойка, условия оплаты, график поэтапной поставки, спецификации?
3. Что считать источником истины при расхождении: договор в ЭДО, учётная система (1С, ERP) или пакет документов?
4. Что пользователь делает дальше с результатом: выгружает отчёт, ставит задачу юристу, пишет поставщику? Отсюда выбор следующей функции.
5. Сколько договоров и документов у одного закупщика, кто ещё смотрит эти данные и какие права доступа нужны?

### Допущения

- Действует правило задания: условия меняет только подписанное обеими сторонами допсоглашение, вступившее в силу к дате проверки. Если подписанное ДС не указывает дату вступления в силу, оно не применяется и помечается для проверки. «С момента подписания» = дата подписания.
- Несколько вступивших ДС применяются по порядку дат вступления в силу. Два ДС с одной датой и разными значениями — конфликт, нужна проверка.
- Номер договора уникален. Документ относится к договору, номер которого есть в заголовке (иначе в тексте). Если упомянуто несколько договоров, документ не привязывается.
- Абзац = непустая строка файла.

### Метрики

1. **Точность без вымысла:** доля значений в таблице, совпавших с ручной сверкой юриста, и отдельно число значений, выданных без опоры на текст. Цель второй метрики — ноль. Измерять на размеченной выборке реальных пакетов.
2. **Время сверки:** время от загрузки пакета до ответа «сумма и срок подтверждены» в сравнении с ручным чтением; плюс доля значений, которые пользователь открыл для проверки по ссылке (показывает доверие).

### Три ключевых решения и компромиссы

1. **Правила вместо LLM.** Результат детерминирован, точно воспроизводится на встрече, цитата всегда дословная, интервьюеру не нужен ключ API. Цена: работает только на знакомых формулировках. LLM — следующий шаг для свободного формата, но в роли извлекателя кандидатов с обязательной проверкой цитаты по исходному тексту.
2. **Лучше «нет данных» и «нужна проверка», чем догадка.** Похожие суммы (аванс, лимит) показываются отдельно с пометкой «не является суммой договора». Цена: на нестандартных документах больше ручной работы.
3. **Статичная страница без сервера и сборки.** Ноль зависимостей, бесплатный хостинг, документы не покидают браузер. Цена: нет хранения, общего доступа и истории.

### 100 000 документов и права доступа

- Загрузка и разбор уходят на сервер: очередь обработки, хранилище исходников, база с извлечёнными полями и ссылками на абзацы (номер документа, версия, смещение цитаты).
- Связь документов по номеру договора и контрагенту по индексу, а не перебором; полнотекстовый поиск для вопросов.
- Права на уровне договора/подразделения: пользователь видит только свои договоры, цитаты и ссылки фильтруются тем же правилом. Журнал, кто какое значение смотрел и подтверждал.
- Ручные подтверждения и исправления сохраняются и служат разметкой для оценки качества правил или модели.

### Три следующих улучшения по приоритету

1. Ставка неустойки и условия оплаты с цитатой: одна запись в `FIELDS` и тест.
2. Ручное подтверждение значения и экспорт таблицы в Excel с цитатами — то, что закупщик делает дальше с результатом.
3. LLM-извлечение для документов свободного формата с проверкой: значение принимается, только если цитата дословно найдена в тексте и проходит те же правила статуса.

## Отчёт о вайбкодинге

**Инструмент:** Claude Code (модель Claude Opus 5.5) в десктопном приложении. Задание и документы скачаны агентом с Яндекс.Диска через публичный API, код, тесты, README и публикация на GitHub Pages сделаны в той же сессии. Перед стартом я сам разобрал документы и выписал ловушки и правильные ответы, этот список служил чек-листом для тестов.

**Время:** около 1 часа 15 минут от скачивания задания до публикации, плюс время на мою проверку и подготовку к демонстрации. Не сделано: см. «Три следующих улучшения» и «Известные ограничения».

**Характерные запросы:**

1. «Создай новый публичный репо для этого тестового, сделай его и залей на GitHub Pages. Смотри на условия, не забудь про README» + мой разбор ловушек (ДС № 1 против проекта ДС № 2, аванс внутри суммы, лимит бюджета вместо стоимости).
2. «Без LLM внутри, на правилах: определить тип документа по заголовку и статусу, связать с договором по номеру, применить только подписанные ДС с датой вступления в силу не позже даты проверки, остальное — отдельным списком».
3. «Тесты: четыре вопроса, отсутствующая сумма, неподписанный проект и новый договор с изменённым полем, никаких зашитых имён файлов».

**Ошибки ИИ и как поймали:**

- В регулярных выражениях ИИ использовал `\bна` для конструкции «с 20.03.2026 на 27.03.2026». В JavaScript `\b` понимает только латиницу, поэтому перед кириллицей граница слова не срабатывает. Предложение поставщика превратилось в «нужна проверка» вместо 27.03.2026. Поймал тест вопроса 4, исправлено на `(?<![а-яё])на`.
- Тип документа определялся по слову «СОГЛАШЕНИЕ», а заголовок проекта — «ПРОЕКТ ДОПОЛНИТЕЛЬНОГО СОГЛАШЕНИЯ» (другой падеж). Проект ДС № 2 не попадал в «не согласовано». Поймал тест вопроса 1, исправлено на основу слова `СОГЛАШЕНИ`.
- При извлечении текста задания из DOCX агент запустил Python с флагом `-I`, который игнорирует `PYTHONIOENCODING`. Текст пришёл кракозябрами. Заметили по выводу, текст переписан в файл явно в UTF-8.
